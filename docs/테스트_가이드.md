## 1. 테스트 환경 준비

### 1.1 사전 요약

- **PostgreSQL**: 스키마 초기화 및 서버 실행
- **Redis**: 세션/그래프 상태 저장
- **`.env`**: DB·Redis·Judge0 등 연결 정보
- **제출·Judge0 연동 테스트**: FastAPI 서버 및 (필요 시) Judge0 Worker 실행

### 1.2 PostgreSQL 실행

```bash
# Docker Compose (개발)
docker-compose -f docker-compose.dev.yml up -d postgres

# 로컬 PostgreSQL 사용 시에는 서비스가 떠 있는지 확인
```

### 1.3 DB 스키마 초기화

```bash
# Docker PostgreSQL
docker exec -i ai_vibe_postgres_dev psql -U postgres -d ai_vibe_coding_test < scripts/init-db.sql

# 로컬 PostgreSQL
psql -U postgres -d ai_vibe_coding_test < scripts/init-db.sql
```

**주요 테이블**

- `exam_participants` (ENUM 타입 포함)
- `prompt_sessions`, `prompt_messages`, `prompt_evaluations`
- `submissions`, `scores`

### 1.4 Redis 실행

```bash
docker-compose -f docker-compose.dev.yml up -d redis
```

로컬 Redis를 쓰는 경우에도 서비스 기동 여부를 확인합니다.

### 1.5 Docker로 인프라만 / 전체 스택 실행

#### 개발용 (`docker-compose.dev.yml`) — PostgreSQL + Redis (+ Adminer)

로컬에서 앱 서버만 띄우고 DB·Redis만 Docker로 쓸 때 사용합니다.

```bash
docker-compose -f docker-compose.dev.yml up -d
docker-compose -f docker-compose.dev.yml logs -f
docker-compose -f docker-compose.dev.yml down
# 볼륨까지 제거 (주의)
docker-compose -f docker-compose.dev.yml down -v
```

- PostgreSQL: `localhost:5435`
- Redis: `localhost:6379`
- Adminer: `http://localhost:8080`  
  - 시스템: PostgreSQL / 서버: `postgres` / 사용자: `postgres` / 비밀번호: `postgres` / DB: `ai_vibe_coding_test`

#### 전체 스택 (`docker-compose.yml`)

PostgreSQL, Redis, AI Worker, Judge Worker 등을 함께 올릴 때 사용합니다.

```bash

docker-compose logs -f ai_worker
docker-compose logs -f judge_worker
docker-compose down
docker-compose down -v   # 데이터 삭제 — 주의
```

- PostgreSQL: `localhost:5432`
- Redis: `localhost:6379`
- AI Worker (FastAPI): `http://localhost:8001`

```bash
curl http://localhost:8001/health
# 브라우저: http://localhost:8001/docs
```

#### 프로덕션 (`docker-compose.prod.yml`)

배포용 별도 설정이 필요합니다.

### 1.6 연결·스키마 문제 해결

| 증상 | 조치 |
|------|------|
| PostgreSQL 연결 거부 (`ConnectionRefusedError` 등) | 서버 기동, `.env`의 `POSTGRES_HOST`·`POSTGRES_PORT`, `docker ps` 확인 |
| `relation "exam_participants" does not exist` | `scripts/init-db.sql` 실행 (일부 테스트 스크립트는 테이블 자동 생성을 지원할 수 있음) |
| ENUM 값 오류 (`invalid input value for enum`) | ENUM 재생성 또는 `init-db.sql`로 스키마 재적용 |
| Redis 연결 실패 | 서버 기동, `.env`의 `REDIS_HOST`·`REDIS_PORT`, `docker ps` 확인 |

## 2. 테스트 스크립트 사용법

프로젝트 루트에서 실행합니다. DB 설정은 `.env`를 따릅니다. 가능하면 `uv run python ...` 형태를 권장합니다.

### 2.1 유닛·노드 테스트

| 파일 | 용도 |
|------|------|
| `test_scripts/test_node4_intent_only.py` | Node 4(Turn Evaluator) 의도 분석·평가 확인 |

```bash
# 대화형
python test_scripts/test_node4_intent_only.py

# 인자 모드
python test_scripts/test_node4_intent_only.py "사용자 메시지" "AI 응답" [spec_id] [--save-db]
```

- 출력: 의도·신뢰도, 턴/루브릭 점수, LLM 근거, 토큰, (선택) DB 저장
- `--save-db`: 평가 결과 DB 저장 (기본 False)
- `spec_id` 기본값: 2098

### 2.2 더미·세션 데이터

| 파일 | 용도 |
|------|------|
| `test_scripts/create_chat_session.py` | 단일 채팅 세션 (session_id=1), Admin·Exam·Participant·Problem·PromptSession 등 |
| `test_scripts/create_dummy_chat_sessions.py` | 여러 세션 일괄 생성 (`uv run python test_scripts/create_dummy_chat_sessions.py 5`) |
| `test_scripts/insert_prompt_messages.py` | 기존 세션에 메시지 삽입 (JSON 또는 입력; `role`은 `USER`/`AI` 대문자, `turn` 고유) |
| `test_scripts/setup_tsp_test_data.py` | TSP 문제용 테스트 데이터 |
| `test_scripts/setup_web_test_data.py` | Chat API용 기본 데이터 (Exam 1, Participant 1, Problem 1, ProblemSpec spec_id 10, ExamParticipant 2, PromptSession 1) |
| `test_scripts/setup_submit_test_data.py` | Submit API용 데이터; **기존 최대 ID 기준 자동 증가**, 생성 ID는 `test_ids.json`에 저장 |

```bash
uv run python test_scripts/setup_web_test_data.py
uv run python test_scripts/setup_submit_test_data.py
```

### 2.4 연결·결과 확인 유틸

| 파일 | 용도 |
|------|------|
| `test_scripts/check_server.py` | 서버 가동 여부 빠른 확인 |
| `test_scripts/check_judge0_connection.py` | Judge0 연결 확인 |
| `test_scripts/check_submit_result.py` | Submit 후 Submission·Scores·턴/홀리스틱 평가·세션 상태 확인 (`test_ids.json` 필요) |

### 2.5 DB·데이터 주의사항

1. 평가 저장 전 해당 `session_id`·`turn`에 메시지가 있어야 합니다.
2. `prompt_messages.role`은 `'USER'` 또는 `'AI'`(대문자)만 허용됩니다.
3. 평가 저장 시 FK로 `prompt_messages`에 행이 있어야 합니다.

테스트 데이터 정리 예(개발 DB에서만):

```sql
DELETE FROM ai_vibe_coding_test.prompt_evaluations;
DELETE FROM ai_vibe_coding_test.prompt_messages;
DELETE FROM ai_vibe_coding_test.prompt_sessions;
-- 필요 시 기타 테이블
```

## 4. 전체 플로우 시나리오

Chat API와 Submit API를 연속 실행해 **평가 파이프라인**을 검증합니다.

### 4.1 목표

1. **Chat API**: 일반 대화(AI 응답만, 이 시나리오 설명상 턴 평가 없음)
2. **Submit API**: 코드 제출 후 전체 평가(예: 4번·6번 노드 등)
3. **결과**: DB의 평가·점수·세션 종료 검증

### 4.2 Phase 1 — 테스트 데이터

스크립트: `test_scripts/setup_submit_test_data.py`

문서 예시 기준 생성 개념(실제 ID는 스크립트가 `test_ids.json`에 기록):

- Exam / Participant / ExamParticipant / PromptSession / Submission 등
- Problem ID 1(외판원), ProblemSpec `spec_id` 10
- 진행 중 세션(`ended_at` NULL), Submission `QUEUED` 등

```bash
uv run python test_scripts/setup_submit_test_data.py
```

### 4.3 Phase 2 — Chat API (`POST /api/chat/messages`)

여러 턴으로 히스토리를 쌓습니다. 아래 `sessionId`·`examParticipantId` 등은 **예시(문서상 1000)**이며, 실제 실행 시에는 `setup_submit_test_data.py`와 `test_ids.json` 값에 맞춥니다.

**Turn 1 예시**

```json
{
  "sessionId": 1000,
  "examParticipantId": 1000,
  "turnId": 1,
  "role": "USER",
  "content": "비트마스킹이 뭔가요?",
  "context": { "problemId": 1, "specVersion": 1 }
}
```

- AI 응답, `messages` 갱신, Redis 저장
- 응답 예: `aiMessage`에 `tokenCount`, `totalToken` 등

**Turn 2 예시**

```json
{
  "sessionId": 1000,
  "examParticipantId": 1000,
  "turnId": 2,
  "role": "USER",
  "content": "DP로 푸는 방법을 알려주세요",
  "context": { "problemId": 1, "specVersion": 1 }
}
```

- `totalToken`은 이전 턴 누적 반영

**Turn 3 (선택)**

```json
{
  "sessionId": 1000,
  "examParticipantId": 1000,
  "turnId": 3,
  "role": "USER",
  "content": "시간 복잡도는 어떻게 되나요?",
  "context": { "problemId": 1, "specVersion": 1 }
}
```

### 4.4 Phase 3 — Submit API (`POST /api/session/submit`)

**요청 예**

```json
{
  "problemId": 1,
  "specVersion": 1,
  "examParticipantId": 1000,
  "finalCode": "import sys\ninput = sys.stdin.readline\n\ndef tsp(current, visited):\n    ...",
  "language": "python3.11",
  "submissionId": 1000
}
```

**처리 개요**

1. `exam_participants`·진행 중 세션 조회
2. Redis에서 State 로드 후 LangGraph 실행
3. **노드 4 (Eval Turn Guard)**: 메시지에서 턴 추출 → Eval Turn 서브그래프 → Redis `turn_logs:{session_id}:{turn}`, PostgreSQL `prompt_evaluations` (`TURN_EVAL`)
4. **노드 6a (Holistic Flow)**: `turn_logs` 기반 전체 플로우 평가 → `HOLISTIC_FLOW`
5. **노드 6b**: `turn_scores` 집계
6. **노드 6c**: Judge0로 실행·정확성·성능
7. **노드 7**: 최종 점수(Prompt 40%, Correctness 30%, Performance 30%), 등급 → `scores`, `rubric_json`(실행 시간·메모리 등)

**응답 예**

```json
{
  "submissionId": 1000,
  "status": "successed"
}
```

### 4.5 Phase 4 — 결과 확인

`test_scripts/check_submit_result.py`로 다음을 확인합니다.

- `submissions`: 상태, `code_inline`
- `scores`: `prompt_score`, `perf_score`, `correctness_score`, `total_score`, `rubric_json`의 `grade`, `performance_details` 등
- `prompt_evaluations`: `TURN_EVAL`, `HOLISTIC_FLOW`
- `prompt_sessions`: `ended_at`

### 4.6 플로우 다이어그램

```
[Phase 1] 데이터 준비
    ↓
[Phase 2] Chat (Turn 1~3…) → Writer → State/Redis, 평가 없음
    ↓
[Phase 3] Submit → State 로드 → LangGraph
    → 노드4 턴 평가 → turn_logs / prompt_evaluations
    → 6a Holistic Flow → prompt_evaluations
    → 6b 집계 → 6c Judge0 → 7 최종 점수 / scores
    ↓
[Phase 4] check_submit_result / DB 검증
```

### 4.7 실행 순서 (권장)

```bash

docker-compose -f docker-compose.dev.yml up -d

# 터미널 2
```

### 4.8 검증 체크리스트

**Chat**

- [ ] 턴마다 AI 응답
- [ ] `tokenCount` / `totalToken` 누적
- [ ] State·Redis 반영
- [ ] 일반 채팅 구간에서 불필요한 턴 평가가 없음(설계 의도 기준)

**Submit**

- [ ] 노드 4·6a·6c·7 동작(로그)
- [ ] Redis `turn_logs`, PostgreSQL `prompt_evaluations`(TURN_EVAL, HOLISTIC_FLOW)
- [ ] Judge0·점수·`scores`·`rubric_json`(실행 시간·메모리)

**데이터**

- [ ] `submissions`, `scores`, `prompt_evaluations`, `prompt_sessions.ended_at`

### 4.9 주의·예상 시간

- FastAPI 필수; Judge0는 사용 시 Worker·환경 변수 필요
- `scripts/init-db.sql`·ENUM 준비
- Redis 필수
- Submit은 평가 완료까지 대기(문서 기준 최대 약 5분 등, 환경에 따라 변동)
- 문서 예시 ID(1000 등)와 실제 `test_ids.json` 불일치 시 요청 본문을 맞출 것

# v2.1 평가 구조 및 점수 합산 방식 정리

> **목적**: 채점 구조 변경·파인튜닝용 점수 책정을 다른 AI에서 진행할 때 참고할 **현재 평가 구조**와 **Step 1~6에서 변화된 사항** 요약.  
> **기준**: Step 01~06 완료 후 코드베이스 (`scores.py`, `integrated_evaluator.py`, `turn_evaluator`, `eval_turn_guard` 등).

---

## 1. 평가 플로우 개요

```
[제출 전] 턴별 대화
    → Eval Turn SubGraph (Node 4): 턴마다 Intent 분석 + 턴별 루브릭 평가 (clarity, problem_relevance, rules, examples, context)
    → turn_scores, turn_analyses 누적

[제출 시] 코드 제출
    → 6a: Holistic Flow (체이닝 전략 등) → holistic_flow_score
    → 6b: 턴 점수 집계 → aggregate_turn_score
    → 6b: Integrated Evaluator → integrated_score, integrated_evaluation (rubric_breakdown, code_quality_metrics)
    → 6c: Correctness (Judge0 테스트) → code_correctness_score
    → 6c: Performance (Judge0 실행/메모리) → code_performance_score
    → 7: aggregate_final_scores → prompt_score, total_score, grade (A~F)
```

- **터널 평가**: `eval_turn_guard` → Intent 분석 → 턴별 루브릭(5항목) 가중치 적용 → `turn_score` 저장.
- **통합 평가**: 제출 코드에 대해 Radon CC, ΔCC(v1 vs v2), AST 패턴, 5대 루브릭 → `integrated_evaluation`.
- **최종 집계**: `app/domain/langgraph/nodes/holistic_evaluator/scores.py`의 `aggregate_final_scores`.

## 2. 최종 점수 합산 (aggregate_final_scores)

### 2.1 대영역 가중치 (v2.1)

| 영역 | 비율 | 설명 |
|------|------|------|
| **Prompt** | 40% | 프롬프트 활용도 (턴 평가 + 플로우 + 통합 평가 블렌딩) |
| **Correctness** | 40% | Judge0 테스트 케이스 통과율 |
| **Performance** | 20% | Judge0 실행 시간/메모리 (성능 점수). Radon CC 보정 가능 |

- **참고**: 이전 40/30/30에서 **Correctness 40%, Performance 20%**로 변경됨 (파인튜닝·기능 정확성 강조).

### 2.2 Prompt Score 계산

1. **기본**: `holistic_flow_score` 60% + `aggregate_turn_score` 40%  
   - `aggregate_turn_score`: 턴별 `turn_score`의 **평균**.
2. **Step 05 반영**: `integrated_score`가 있으면 기존 prompt_score와 **50:50 블렌딩**.  
   - `prompt_score = prompt_score * 0.5 + integrated_score * 0.5`

### 2.3 Total Score 공식

```text
total_score = prompt_score × 0.40 + correctness_score × 0.40 + perf_score × 0.20
```

- `perf_score`: 필요 시 Radon CC(avg_cc)에 따라 0.8~1.0 배율 적용 (클린 코드일수록 성능 가산).

## 3. 프롬프트 평가 방식 (상세)

프롬프트 점수(Prompt Score)는 **세 가지 평가 결과**를 조합해 만든다.

1. **턴별 평가** → 각 턴의 `turn_score` → 평균한 값이 `aggregate_turn_score`
2. **Holistic Flow 평가(6a)** → 전체 대화의 체이닝 전략 점수 `holistic_flow_score`
3. **Integrated Evaluator(6b)** → 제출 코드·턴 분석 기반 통합 점수 `integrated_score` (있으면 prompt에 50% 블렌딩)

아래는 각 단계의 입력·기준·산출을 정리한 것이다.

---

### 3.1 턴별 평가 (Eval Turn SubGraph) — 턴당 1회

**역할**: 사용자가 **해당 턴에서 보낸 프롬프트(지시문)**만 평가. AI 응답은 참고용.

**실행 시점**: 제출 시, 저장된 모든 턴에 대해 `_evaluate_turn_sync`로 순차 실행.

**흐름**:
1. **Intent 분석** (Node 4 내부): 사용자 메시지 → 8가지 의도 중 분류 (GENERATION, OPTIMIZATION, DEBUGGING, TEST_CASE, HINT_OR_QUERY, RULE_SETTING, FOLLOW_UP, SYSTEM_PROMPT). v2.1에서는 4대 통합 의도(SETTING/CREATION/REFINEMENT/VALIDATION)로도 매핑·저장.
2. **다중 Evaluator 실행**: 위 8가지에 대응하는 evaluator 중 **실제로 의도로 판별된 evaluator**가 LLM을 호출. (rule_setting_eval, generation_eval, optimization_eval, debugging_eval, test_case_eval, hint_query_eval, follow_up_eval 등.)
3. **각 evaluator가 LLM으로 산출하는 것**:  
   - **5대 루브릭** 항목별 점수(0~100) + reasoning.  
   - 루브릭 키: **명확성(Clarity)**, **문제 적절성(Problem Relevance)**, **예시(Examples)**, **규칙(Rules)**, **문맥(Context)**.  
   - 프롬프트: `eval_turn.yaml` 기반. 평가 유형(eval_type)별로 **criteria**가 다름 (예: generation이면 "입출력 예시·구현 조건 상세 기술" 등).
4. **의도별 가중치 적용** (`turn_evaluator/weights.py`):  
   - `calculate_weighted_score(rubrics, intent, context_override_100)`  
   - `INTENT_WEIGHTS[intent]`에 따라 루브릭별 가중치가 다름.  
   - 예: GENERATION → rules 0.3, clarity 0.25, examples 0.25, problem_relevance 0.1, context 0.1.  
   - FOLLOW_UP → context 0.8, clarity 0.2 등.
5. **Human-Centric 보정** (같은 파일):  
   - **Examples**, **Rules**가 0점이면 **70점으로 중립 처리** (가산점 항목이라 없어도 감점하지 않음).  
   - **Phase 2 첫 턴** (`is_phase2_first_turn=True`, SAVE 직후 턴): **Context**를 **100점**으로 간주 (`context_override_100`).
6. **여러 evaluator 점수 합침**: 해당 턴에서 실행된 모든 evaluator의 **가중 점수**를 **평균** 내서 해당 턴의 **turn_score**로 사용.
7. **하단 방어선** (`aggregation.py`):  
   - **Clarity**와 **Problem Relevance**가 **둘 다 90 이상**이면 턴 점수 하한 **85** 적용.  
   - `turn_score = max(turn_score, 85.0)`.
8. **가드레일 위반** 시: 해당 턴 **turn_score = 0**.

**정리**: 턴마다 “사용자 프롬프트가 5대 루브릭(명확성·문제 적절성·예시·규칙·문맥)을 얼마나 만족하는지”를 의도별 가중치로 합산하고, Human-Centric·하단 방어선·가드레일을 적용한 값이 **turn_score**이다.

---

### 3.2 Holistic Flow 평가 (Node 6a, eval_holistic_flow)

**역할**: **전체 대화**에서 사용자 프롬프트의 **체이닝 전략**(문제 분해, 피드백 수용, 주도성, 전략적 탐색)을 평가.  
**평가 대상은 “사용자 프롬프트”만**이며, AI 응답 품질은 점수에 반영하지 않음.

**입력**:
- Redis(및 필요 시 DB)에서 조회한 **모든 턴의 turn_log**  
- 턴별: intent, user_prompt_summary, ai_summary, score, rubrics 등  
- 문제 정보(problem_context)는 시스템 프롬프트에 포함

**LLM 산출** (`HolisticFlowEvaluation` 구조체, `eval_holistic_flow.yaml` 기준):
- **problem_decomposition** (0~100): 문제를 단계적으로 나누어 요청했는지, 문제 특성·힌트 로드맵에 맞는 접근인지.
- **feedback_integration** (0~100): 이전 턴의 AI 힌트를 다음 프롬프트에 반영했는지.
- **strategic_exploration** (0~100): 의도 전환(예: HINT_OR_QUERY → OPTIMIZATION) 등 전략적 탐색이 있는지.
- **overall_flow_score** (0~100): 위 항목들을 종합한 **전체 플로우 점수** (가중 평균).
- **analysis** (텍스트): 주도성·오류 수정, 고급 프롬프트 기법(XML, Few-shot 등)에 대한 설명. 항목 3·5는 점수 필드에는 없고 analysis에만 기재.

**저장**: `holistic_flow_score` = `overall_flow_score`, `holistic_flow_analysis` = `analysis`.

---

### 3.3 턴 점수 집계 (aggregate_turn_scores, 6b)

- **입력**: `state["turn_scores"]` (턴 번호 → 해당 턴의 `turn_score` 등).
- **연산**: 모든 턴의 `turn_score`를 **평균**.
- **산출**: `aggregate_turn_score` (0~100).

---

### 3.4 Prompt Score로의 합산 및 Integrated 반영

1. **1차 합산** (scores.py):  
   `prompt_score = holistic_flow_score × 0.60 + aggregate_turn_score × 0.40`  
   (둘 중 하나만 있으면 그 값만 사용.)
2. **Integrated 반영** (Step 05):  
   `integrated_score`가 존재하고 0 이상이면:  
   `prompt_score = prompt_score × 0.5 + integrated_score × 0.5`  
   (기존 prompt_score가 0이면 integrated_score만 사용.)
3. **최종 Total**에서는 이 **prompt_score**가 40% 가중치로 들어감 (2절 참고).

**요약**: 프롬프트 평가는 **(1) 턴별 5대 루브릭 + 의도별 가중치 → turn_score 평균**, **(2) Holistic Flow 4항목 → overall_flow_score**, **(3) 제출 코드·턴 분석 기반 integrated_score**를 60:40 후 50:50 블렌딩해 하나의 **Prompt Score**로 만든다.

## 4. 학점(Grade) 산정 — 파인튜닝·설계 반영

v2.1에서는 **Correctness(동작)** 와 **설계 지표(ΔCC, AST)** 를 결합해 학점을 낸다.  
**기능 100점이라도 설계가 나쁘면 B 이상 불가.**

### 4.1 Correctness 미달

- `correctness_score < 100` → **D** (60 이상) 또는 **F** (60 미만).

### 4.2 Correctness 100일 때 (설계 지표 적용)

`code_quality_metrics`가 있을 때 (스마트 게이트 2026 등):

| 조건 | 학점 |
|------|------|
| ΔCC ≤ 10% **AND** `ast_pattern_matched == True` | **A** (Senior) |
| ΔCC ≤ 30% **AND** avg_cc < 8 | **B** (Mid) |
| ΔCC > 60% **OR** (ast_applicable **AND** not ast_pattern_matched) | **C** (Junior) |
| 그 외 | **C** (설계 미달로 B 이상 불가) |

- **ΔCC**: v1 대비 v2 코드의 순환 복잡도 상승률(%).  
- **ast_pattern_matched**: SecurityRule → BaseRule 상속, GateManager 전략 패턴 유지 여부 (AST 검사).  
- **ast_applicable**: 해당 문제가 AST 검사 대상인지 (spec_id=20 스마트 게이트 2026 전용 등).

`code_quality_metrics`가 없으면(다른 문제): **총점만**으로 A/B/C/D/F 구간 적용 (90/80/70/60).

## 5. 턴별 평가 (Eval Turn) — 루브릭·가중치 요약

- **파일**: `app/domain/langgraph/nodes/turn_evaluator/weights.py`, `aggregation.py`, `eval_turn_guard.py`.
- **5대 루브릭 키**: rules, clarity, examples, problem_relevance, context (한글명은 `RUBRIC_NAME_MAP`으로 매핑).
- **의도별 가중치**: GENERATION, OPTIMIZATION, DEBUGGING, TEST_CASE, HINT_OR_QUERY, RULE_SETTING, FOLLOW_UP, SYSTEM_PROMPT 등마다 다름 (`INTENT_WEIGHTS`).
- **Human-Centric**: Examples·Rules가 0점이어도 감점하지 않고 70으로 중립 처리. Phase 2 첫 지시 시 Context 100 처리 옵션(`context_override_100`).
- **가드레일 위반** 시 해당 턴 점수 0.  
- **Clarity·Problem Relevance 모두 ≥90**이면 턴 점수 하한 85 적용.

## 6. Integrated Evaluator (Node 6b) — 5대 루브릭·CC·AST

- **파일**: `app/domain/langgraph/nodes/integrated_evaluator.py`, `app/domain/langgraph/utils/code_quality.py`.
- **code_quality_metrics**:  
  - Radon CC (함수별, max_cc, avg_cc), **junior_grade** (CC > 10).  
  - **v1 vs v2 비교**: `delta_cc` (ΔCC %).  
  - **AST**: `ast_pattern_matched`, `ast_applicable` (SecurityRule 상속, GateManager 전략 패턴).
- **rubric_breakdown** (5대 루브릭):  
  - instruction_clarity, design_ownership, logical_gaps, consistency_maintained, **code_improvement_contribution**.  
  - code_improvement_contribution는 AST 일치·CC·ΔCC(10% 이하 가산, 30% 초과 감점) 반영.
- **integrated_score**: turn_analyses + first_prompt/follow_up + rubric_breakdown·code_quality 반영한 통합 점수.

> **대상**: v2.1의 **데이터 추적을 위한 Snapshot 아키텍처** 설계 및 도메인·State·Enum·문제 정의 확장.  
> **선행 조건**: 없음. **가장 먼저** 진행하는 단계.  
> **핵심**: 단순 필드 추가를 넘어, v1(Phase 1 확정) / v2(최종 제출) 코드를 추적할 수 있는 저장 구조를 설계한다.

**기준**: `.maestro/docs/V2.1_Work_Instructions.md`, `.maestro/docs/V2.1_Handoff_Guide_For_Managing_AI.md` §3 Step 01

## 1. 목표

- **State·Enum 확장**: MainGraphState에 v1_code, v2_code, v1_metrics, v2_metrics 추가. GradeType, UnifiedIntentType, RubricType Enum 정의.
- **Snapshot 저장 로직**: 프론트 SAVE(Phase 1 확정) 요청 시 `prompt_messages.meta`에 v1 스냅샷을 기록하는 구조를 설계·구현하여, Step 04에서 v1_code를 복원할 수 있게 한다.
- **문제 정의**: 스마트 게이트 2026 시나리오를 problem_info에 추가 (Phase 1/2, 보안 등급·누적 과금 제약).
- **구조 원칙**: 모든 평가 데이터는 최종적으로 **prompt_evaluations.details (JSONB)**에 통합 저장 가능한 형태로 설계한다.

## 2. 상태 객체(State) 및 도메인 확장

### 2.1 MainGraphState 확장

다음 필드를 추가한다. (기존 필드는 유지, Optional/기본값으로 하위 호환 유지.)

| 필드 | 타입 | 설명 |
|------|------|------|
| `v1_code` | `Optional[str]` | Phase 1 구현 후 사용자가 **SAVE**로 확정한 **Baseline 코드**. |
| `v2_code` | `Optional[str]` | **최종 제출 시점**의 **Final 코드**. |
| `v1_metrics` | `Optional[Dict[str, Any]]` | v1_code에 대한 분석 결과(예: Radon CC 등). Dict/JSONB 호환. |
| `v2_metrics` | `Optional[Dict[str, Any]]` | v2_code에 대한 분석 결과(예: Radon CC, AST 패턴 등). Dict/JSONB 호환. |

**Snapshot 정의 (용어)**:

- **v1_code**: 사용자가 Phase 1 구현 후 **SAVE 버튼**을 눌러 확정된 Baseline 코드.
- **v2_code**: **최종 제출** 시점의 Final 코드.

코드는 항상 **str** 타입으로 관리하고, DB 저장 시에만 JSON 직렬화를 수행한다.

### 2.2 Enum 정의 (String 기반)

`app/infrastructure/persistence/models/enums.py`에 다음을 추가한다.

| Enum | 값 | 비고 |
|------|-----|------|
| **GradeType** | A, B, C, D, F | 최종 학점 (A=Senior ~ F=Fail). |
| **UnifiedIntentType** | SETTING, CREATION, REFINEMENT, VALIDATION | 4대 통합 의도. |
| **RubricType** | SPECIFICITY, DESIGN_CONTROL, ROBUSTNESS, CONSISTENCY, EFFICIENCY | 5대 루브릭. |

## 3. Snapshot 저장 로직 (중요)

v1_code는 **프론트에서 SAVE 요청 시점**에만 확정된다. 이 시점의 코드를 나중에 Step 04에서 v1_code로 사용할 수 있도록 저장해야 한다.

### 3.1 API 계약: SAVE(Phase 1 확정) 대응

- **엔드포인트**: 기존 `POST /api/chat/save-message`(또는 전용 `POST /api/chat/save` 등)를 활용한다.
- **동작**: 프론트에서 **SAVE**(Phase 1 확정) 요청 시, **현재 코드 전체**를 해당 턴의 메시지와 함께 저장한다.
- **저장 위치**: `prompt_messages` 테이블의 **meta (JSONB)** 필드.
- **meta 필수 구조**: 아래를 **반드시** 포함하도록 설계·문서화한다.

```json
{
  "code_snapshot": "코드 전체 텍스트 (str)",
  "is_v1_checkpoint": true
}
```

- `is_v1_checkpoint: true`인 메시지가 나중에 Step 04에서 **v1_code를 찾아내는 유일한 추적 단서**가 된다.
- 구현 시: 클라이언트가 위 구조로 `meta`를 보내면, 기존 `save_message`(또는 동일 역할)에서 `meta`를 그대로 JSONB로 저장하도록 한다. 이미 `meta_dict`로 저장되고 있으면, **요청 스키마·문서**에 위 형식을 명시하고, 필요 시 해당 턴/세션에서 `is_v1_checkpoint === true`인 레코드를 조회해 v1_code를 복원하는 로직을 Step 04에서 사용할 수 있게 한다.

### 3.2 v1_code 복원 (Step 04용 참고)

- Step 04에서는 `prompt_messages`를 턴/세션 기준으로 조회하고, `meta->>'is_v1_checkpoint' = 'true'`인 행에서 `meta->>'code_snapshot'`을 v1_code로 사용한다. (구체 구현은 Step 04 지시문에서 다룸.)

## 4. 문제 정의 (problem_info) 업데이트

`app/domain/langgraph/utils/problem_info.py`의 `HARDCODED_PROBLEM_SPEC`에 **스마트 게이트 2026** 시나리오를 추가한다. (예: `spec_id=20`.)

### 4.1 스마트 게이트 2026 요약

- **Phase 1 (기본)**  
  - 기본 보안 통과 및 수하물 과금 로직.  
  - 여권 만료일(2026-02-04 이전 REJECT), 항공편 상태(BOARDING만 통과, DELAYED=WAIT, 그 외 REJECT), 수하물 무게(이코노미 20kg/비즈니스 30kg 초과 시 CHARGE_FEE 후 통과).
- **Phase 2 (긴급 정책)**  
  - **긴급 보안 등급(HIGH)**: `threat_level == HIGH`이면 모든 승객 SECURITY_CHECK.  
  - **누적 과금 페널티**: 특정 항공편에서 수하물 초과 과금 누적 3명 발생 시, 해당 항공편 4번째 승객부터 허용 무게 **-5kg** 적용.
- **키워드**: GateManager, BaseRule, SecurityRule, 전략 패턴, 규칙 인터페이스, 상속 등 (Writer 분기·평가 시 사용).
- **평가 포인트**: Rule 인터페이스 분리, SecurityRule이 BaseRule 상속, GateManager 전략 패턴 유지.

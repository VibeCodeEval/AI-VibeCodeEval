## 1. 시스템 목적 및 핵심 로직

본 테스트는 사용자가 LLM을 활용하여 코드를 작성할 때, **요구사항의 복잡화(2차 시나리오)**에 직면해서도 설계의 일관성을 유지하고 AI를 논리적으로 통제(Steering)하는 능력을 평가한다.

**평가 핵심**:
- **구조적 탄력성**: 2차 요구사항 추가 시 기존 설계(인터페이스·패턴)를 유지·확장하는지
- **프롬프트 제어 능력**: 구조적 용어(인터페이스, 상속, 전략 패턴 등)로 AI를 통제했을 때 코드 품질(복잡도·아키텍처)이 개선되는지

---

## 2. 예시 문제: 스마트 게이트 2026 보안 엔진

수험자는 아래 시나리오를 바탕으로 공항 검문 시스템을 단계별로 구축한다.

### 2.1 Phase 1: 기초 통과 로직 구현 (1차 요구사항)

**배경**: 2026년 차세대 공항 게이트 시스템은 승객의 상태에 따라 통과 여부를 결정한다.

**검증 규칙**:
- **여권 검사**: 여권 만료일이 현재 날짜(2026-02-04) 이전이면 REJECT.
- **항공편 상태**: 항공편 상태가 BOARDING일 때만 통과, DELAYED면 WAIT, 그 외는 REJECT.
- **수하물 무게**: 좌석 등급별 허용량(이코노미 20kg, 비즈니스 30kg) 초과 시 추가 요금(CHARGE_FEE) 부과 후 통과.

**평가 포인트**: 단순 if-else 구현인지, 향후 추가 규칙을 고려해 규칙(Rule) 인터페이스를 분리했는지 확인.

### 2.2 Phase 2: 긴급 정책 변경 대응 (2차 요구사항)

1차 코드 제출 후, 예고 없이 아래 **복합 제약 조건**을 투입하고 코드 수정을 요구한다.

- **긴급 보안 등급 (Security Level)**: 시스템 외부 변수 `threat_level`이 HIGH로 격상되면, 기존 모든 규칙보다 우선하여 모든 승객을 정밀 검사(SECURITY_CHECK) 단계로 보낸다.
- **누적 과금 페널티**: 특정 항공편(Flight)에서 수하물 초과 과금을 받은 승객이 누적 3명이 되면, 해당 항공편의 4번째 승객부터는 허용 무게 기준을 일괄 **-5kg** 강화한다.

**평가 포인트**:
- **조건부 우선순위**: if문을 덕지덕지 붙인 스파게티 코드인가?
- **상태 관리**: 누적 데이터를 위해 설계 구조를 유연하게 변경·확장했는가?

## 3. 노드별 상세 지시 사항

### 3.1 Writer LLM (Node 3)

| 사용자 지시 유형 | Writer 동작 |
|------------------|-------------|
| **모호한 지시** (예: "2차 요구사항 반영해줘") | `check_passenger` 등 한 함수 안에 로직을 몰아 넣은 **복잡도 높은 코드**를 제공하여, 사용자의 리팩토링 지시를 유도한다. |
| **구조적 지시** (예: "기존 규칙 인터페이스를 상속받아 SecurityRule을 추가해줘") | **클린 아키텍처** 응답(규칙 인터페이스·전략 패턴 유지, SecurityRule이 BaseRule 상속)을 제공한다. |

**구현 시 유의**: 사용자 메시지에서 "규칙 인터페이스", "상속", "BaseRule", "SecurityRule", "전략 패턴" 등 **구조적 용어**가 포함되면 클린 응답, 그렇지 않으면 스파게티 응답으로 분기한다.

### 3.2 Integrated Evaluator (Node 6b)

| 항목 | 지시 내용 |
|------|-----------|
| **Radon CC** | 2차 수정 후 **함수 하나당 순환 복잡도(Cyclomatic Complexity)가 10을 초과**하면 '주니어급'으로 분류한다. |
| **AST 분석** | 다음을 **물리적으로** 확인한다. (1) `SecurityRule`이 기존 `BaseRule`을 상속받았는지, (2) `GateManager`가 전략 패턴(Strategy Pattern)을 유지하고 있는지. |

**구현 시 유의**: Radon 라이브러리 연동 및 Python AST 기반 상속·전략 패턴 검사 로직을 추가한다.

## 4. 통합 의도(Intent) 및 루브릭 (v2.1 명칭)

### 4.1 4대 통합 의도

| 의도 | 설명 |
|------|------|
| **설계 판 짜기 (Setting)** | AI의 페르소나 및 초기 아키텍처 방향 설정 |
| **기능 만들기 (Creation)** | 1/2차 비즈니스 로직 구현 지시 |
| **코드 다듬기 (Refinement)** | 복잡도 해결을 위한 리팩토링 및 패턴 적용 지시 |
| **검증하기 (Validation)** | 엣지 케이스·테스트 요청 |

기존 8가지 의도(SYSTEM_PROMPT, RULE_SETTING, GENERATION 등)를 위 4대로 매핑·통합하거나, 평가 시 4대 의도 기준으로 집계하도록 변경한다.

### 4.2 5대 직관적 루브릭

※ 파인튜닝 시 가중치·문구 변경 가능.

| 루브릭 | 설명 |
|--------|------|
| **지시의 구체성** | 목표와 제약 조건을 얼마나 명확하게 명시했는가? |
| **설계 주도권** | AI에게 맡기지 않고 패턴(Strategy, State 등)을 직접 제안했는가? |
| **논리적 빈틈없음** | 보안 등급과 누적 과금의 복잡한 상관관계를 정확히 이해했는가? |
| **일관성 유지** | 2차 수정 시 기존 인터페이스를 파괴하지 않고 우아하게 연결했는가? |
| **코드 개선 기여도** | 사용자의 개입 전후로 Radon 복잡도가 얼마나 안정화되었는가? |

## 5. 파인튜닝 데이터 수집 가이드

- **데이터 페어**: `(수정 프롬프트, 코드의 CC 변화, AST 패턴 일치 여부)`
- **학습 핵심**: 사용자가 **구조적 용어**로 AI를 통제했을 때 **코드 복잡도가 낮아지는 현상**을 모델이 '고득점'으로 인식하도록 학습 데이터를 구성한다.

**수집 항목 예시**:
- `modification_prompt`: 사용자가 2차 수정을 요청한 텍스트
- `cc_before` / `cc_after`: 수정 전·후 함수별 Cyclomatic Complexity (또는 최대 CC)
- `ast_pattern_matched`: SecurityRule 상속 여부, GateManager 전략 패턴 여부 (boolean 또는 세부 플래그)
- `label` 또는 `score`: 고득점/저득점 (파인튜닝 타깃)

## 6. AST 계획 전면 수정 방향

- **기존 Phase 6A**: AST 기반 Error Injection(Spec 부족 시 코드 변형) 중심이었음.
- **v2.1 방향**:
  - **평가 측**: 제출 코드에 대한 **Radon CC** 및 **AST 패턴 검사**(상속, 전략 패턴)를 Integrated Evaluator에 포함한다.
  - **Writer 측**: 사용자 지시가 **구조적 용어**인지 **모호한 지시**인지에 따라 응답을 **클린 아키텍처 vs 스파게티**로 분기한다.
  - **파인튜닝**: (수정 프롬프트, CC 변화, AST 패턴 일치) 데이터 페어를 수집하는 파이프라인을 둔다.

`.maestro/docs/code_modification_plan.md` 및 `.maestro/PHASE6_PLAN.md`를 위 방향에 맞춰 **전면 수정**할 것.  
(실제 코드 수정은 이 지시문을 반영한 별도 태스크/커맨드로 진행.)

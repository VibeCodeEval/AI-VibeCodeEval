## Hybrid 평가 모델 (1~5 Likert + 진단 태그)

### 목표
가중치 합산 로직 폐기, **1~5 Likert 척도** 기반 Hybrid 평가로 전환. LLM은 1~5 정수와 진단 태그만 출력하고, Backend에서 고정 매핑으로 0~100 환산.

### 매핑 (SCORE_MAPPING)
| Likert | 의미     | Backend |
|--------|----------|---------|
| 5      | Excellence (탁월) | 100 |
| 4      | Good (우수)      | 90  |
| 3      | Neutral (보통)   | 80  |
| 2      | Weak (미흡)      | 60  |
| 1      | Bad (나쁨)       | 0   |

### 변경 파일
- **app/domain/langgraph/nodes/turn_evaluator/grading.py** (신규)
  - `SCORE_MAPPING`, `likert_to_final()`, `final_to_likert()`
  - `EvaluationResult` (likert_score, final_score, diagnosis_profile, feedback_summary)
  - `DiagnosisProfile`, `evaluation_result_from_payload()`
- **app/domain/langgraph/nodes/turn_evaluator/weights.py**
  - **삭제**: (신규 경로에서) `INTENT_WEIGHTS` / `INTENT_WEIGHTS_V21`, `calculate_weighted_score`, `get_weights_for_intent`, `get_weight_for_rubric`, `_rubric_score_to_likert`
  - **유지**: `RUBRIC_NAME_MAP`, `NEW_INTENT_GROUPS`, `INTENT_GROUP_MAP`, `intent_to_group()`
  - **추가**: `RUBRIC_DISPLAY_ORDER`; **Legacy Adapter**(TODO 삭제 예정): `LEGACY_INTENT_WEIGHTS`, `legacy_turn_score_from_rubrics()`
- **app/domain/langgraph/nodes/turn_evaluator/aggregation.py**
  - 턴 점수: **Tier 1** final_score/likert_score → **Tier 2** score/average → **Tier 3** Legacy Adapter(rubrics). TODO 주석 명시.
- **app/domain/langgraph/nodes/eval_turn_guard.py**
  - `get_weights_for_intent` 제거, 루브릭 표시 순서는 `RUBRIC_DISPLAY_ORDER` 사용
- **app/application/services/eval_service.py**
  - 동일하게 `RUBRIC_DISPLAY_ORDER` 기반 응답 형식 유지

### 점진적 전환 지원 (Priority Queue)
YAML이 아직 Legacy(0~100)이므로, **V2.1(1~5) 우선 지원 + Legacy Fallback**으로 동작한다.

- **Tier 1 (New)**: `likert_score` 또는 `final_score` 있음 → 환산표 적용하여 사용.
- **Tier 2 (Legacy)**: 없으면 `score` / `average` 그대로 사용. (`# TODO: 모든 프롬프트가 V2.1로 전환된 후 삭제 예정`)
- **Tier 3 (Fallback)**: 둘 다 없고 `rubrics`만 있으면 **Legacy Adapter**로 가중 합산하여 사용. (`# TODO: ... 삭제 예정`)

Legacy 처리 로직에는 위 TODO 주석을 달아 두었으며, 전환 완료 후 삭제·아카이빙 예정.

### 혼용 (Hybrid + Legacy)
한 턴에서도 evaluator별로 Tier 1 / Tier 2 / Tier 3가 섞여 있어도, evaluator당 하나의 점수만 골라 평균을 낸다.

**예시**
- `generation_eval`이 `{ "score": 85, "rubrics": [...] }` → **85** (Tier 2).
- `follow_up_eval`이 `{ "likert_score": 4 }` → **90** (Tier 1).
- `hint_query_eval`이 `{ "rubrics": [...] }` 만 있으면 → Legacy Adapter 계산값 (Tier 3).

### Legacy Adapter (조건부 격리)
- **weights.py**: `LEGACY_INTENT_WEIGHTS`, `legacy_turn_score_from_rubrics(rubrics, intent, context_override_100)` — 신규 로직과 섞이지 않게 Tier 3에서만 호출. 동일 TODO 주석 및 삭제 후 아카이빙 안내.

### 데이터 구조
- **EvaluationResult**: `likert_score`는 **Optional** (Legacy 응답 시 없어도 에러 없음). **출력(Output)**은 항상 `final_score`가 채워진 상태로 통일하여 downstream(Holistic Flow 등)에 전달.
- **evaluation_result_from_payload**: Legacy `score`/`average`가 있으면 `final_score`로 채움.

### 검증 (테스트)
- **tests/test_turn_evaluator_hybrid.py**: Legacy 입력(score 85) → 85, New 입력(likert 4) → 90, Tier 3(rubrics만) → Legacy Adapter 값 반환 확인.

### 의도 그룹별 로직 (프롬프트/YAML 추후 반영)
- SETTING: 4점 = Clarity High, 5점 = Clarity High + Rules
- CREATION: 4점 = 명확한 지시, 5점 = 명확 + (Rules OR Examples)
- REFINEMENT: 2점 = 모호한 수정 지시 + clarity_tier Low
- FOLLOW_UP: 3점 = 단순 승인, 5점 = strategic_direction True

### 추적
- 프롬프트(YAML) 수정은 추후 작업. 현재는 Python 구조체·매핑·집계 로직만 반영.

  - 5대 루브릭 `rubric_breakdown`: instruction_clarity, design_ownership, logical_gaps, consistency_maintained, code_improvement_contribution (turn_analysis·CC·AST 반영).

### Step 04 보강: v1 vs v2 비교, ΔCC 산정
- **SessionRepository**: `get_v1_checkpoint_code(session_id)` 추가 — `prompt_messages.meta`에서 `is_v1_checkpoint=true`인 메시지의 `code_snapshot` 반환.
- **integrated_evaluator**: 제출 시 `state["v1_code"]` 또는 DB에서 v1 코드 조회 후, v1/v2 각각 Radon CC 계산 → **ΔCC(상승률)** = (v2_avg_cc - v1_avg_cc) / max(v1_avg_cc, 0.01) * 100. `code_quality_metrics`에 `v1_metrics`, `v2_metrics`, `delta_cc` 포함.
- **code_quality.py**: `compute_delta_cc(v1_radon_result, v2_radon_result)` 추가.
- **rubric_breakdown**: `has_v1`일 때만 ΔCC 반영 — 10% 이하 가산, 30% 초과 감점.

### AST·Step 05 연결 보강
- **AST 범위**: `check_ast_patterns(code, spec_id)` — **스마트 게이트 2026(spec_id=20) 전용**. 정답 구조만 검사: SecurityRule이 BaseRule(또는 Rule) 상속, GateManager 클래스가 규칙 리스트 보유·순회·적용. spec_id≠20이면 `applicable=False`, `ast_pattern_matched=True` 반환(다른 문제는 감점 없음). 루브릭에서는 `ast_applicable`일 때만 AST 보너스 적용.
- **aggregate_final_scores (Step 05)**:
  - `integrated_score`를 prompt_score에 블렌딩(50% 반영).
  - `code_quality_metrics`·`rubric_breakdown` 존재 시 학점 보정: has_v1 & ast_applicable일 때 ΔCC≤10% & avg_cc<5 & AST 일치면 한 단계 상향, ΔCC>30% 또는 code_improvement_contribution<40이면 한 단계 하향.
  - `final_scores`에 `v21_summary`(rubric_breakdown, code_quality_metrics 요약) 포함해 DB/API 저장.

### AST 문제별 패턴 확장 (required_patterns)
- **check_ast_patterns(code, spec_id=None, required_patterns=None)**  
  - `required_patterns`: 문제별 필수 클래스/상속 관계 리스트. 넘기면 해당 패턴만 검사.  
  - 패턴 타입: `inheritance`(class_name, base_names), `strategy_pattern`(class_name, rules_attr_contains, apply_methods_contain).  
  - `required_patterns` 없고 spec_id=20이면 `SMART_GATE_2026_PATTERNS` 사용.  
  - 다른 문제는 `problem_context["ast_required_patterns"]` 등에서 리스트 넘겨 사용 가능.

## 이전 턴 대화 요약 반영 (Eval Turn 입력 확장)

### 목표
턴 N 평가 시 **그 턴만** 보지 않고, **이전 턴(1 ~ N-1)의 대화 요약**을 함께 넘겨서 "이미 1턴에서 상세 지시를 했고, 이번 턴은 '진행해줘' 같은 연속 요청"인 경우 턴 단위에서도 높게 줄 수 있게 함. Holistic Flow가 턴별 요약본으로 전체를 보는 것과 동일한 요약을 **Eval Turn 입력**에도 사용.

### DB 저장 요소
- **새 테이블/컬럼**: 없음. "이전 턴 요약"은 **평가 시 입력으로만** 사용하고, 턴별로 저장하는 항목은 기존과 동일.
- **선택적 보강**: PostgreSQL `prompt_evaluations.details`에는 현재 `ai_summary`만 있고 `user_prompt_summary`는 없음. Holistic이 Redis turn_log의 `user_prompt_summary`를 쓰는 것과 맞추려면, **details에 `user_prompt_summary`(또는 `prompt_summary`) 필드 추가**를 권장. (리포팅·재평가 시 DB만으로 턴별 사용자 요약 복원 가능)

### 예시: 턴 3개 (user+ai 쌍 3개 = 메시지 6턴) 평가 시

**이미 있는 것**
- Holistic Flow는 **Eval Turn에서 나온 턴별 로그**를 Redis에서 읽어 `structured_logs`로 씀. 각 턴당:
  - `prompt_summary` = `user_prompt_summary` (사용자 프롬프트 요약)
  - `ai_summary` = `llm_answer_summary` (AI 응답 요약)
- 즉, **첫 번째 Turn 평가가 끝나면** 그 턴의 "사용자 프롬프트 평가본 + 사용자·AI 요약본"이 이미 생성됨.

**플로우 (같은 요약본을 다음 턴 평가에 바로 사용)**

1. **Turn 1 평가**
   - 입력: `(human_message_1, ai_message_1)`, `previous_turns_summary` = 없음.
   - 출력: 점수·루브릭 + **요약본**  
     - `user_prompt_summary` (현재는 human_message 앞 200자 또는 추후 LLM 요약)
     - `llm_answer_summary` (summarize_answer 노드 결과)
   - Guard가 이 둘을 합쳐 **"Turn 1 요약"** 문자열로 보관.

2. **Turn 2 평가**
   - 입력: `(human_message_2, ai_message_2)` + **previous_turns_summary** =  
     `[Turn 1]\n사용자 요약: {user_prompt_summary}\nAI 요약: {llm_answer_summary}`
   - Eval Turn 프롬프트에 "[이전 턴 요약]" 블록으로 위 문자열 삽입 → "1턴에서 이미 지시했고, 2턴은 진행 요청"인지 판단 가능.
   - 평가 후 Turn 2 요약본 생성 → **"Turn 1 요약" + "Turn 2 요약"** 누적.

3. **Turn 3 평가**
   - 입력: `(human_message_3, ai_message_3)` + **previous_turns_summary** =  
     Turn 1 요약 + Turn 2 요약 (Holistic이 보는 것과 동일한 형태로 이어붙인 문자열).
   - 이후 동일.

**정리**
- **새로 만드는 요약이 아님.** Turn 평가가 끝날 때마다 이미 나오는 **사용자 프롬프트 평가본·사용자·AI 요약본**을 그대로 다음 턴 평가 입력에 넣으면 됨.
- Holistic이 "턴별 대화 요약본"을 보는 것처럼, **평가 대상 턴이 3개면**  
  - 1턴 진행 후 요약본 생성 → 2턴 평가에 사용,  
  - 2턴 진행 후 요약본 누적 → 3턴 평가에 사용.

### Eval Turn(이전 턴 요약 반영) vs Holistic — 통합이 아닌 보완
같은 **요약본**(user_prompt_summary, llm_answer_summary)을 쓰지만, **역할이 다름**. 하나의 평가로 합쳐지는 것이 아니라 둘 다 유지하고 보완 관계로 둠.

| 구분 | Eval Turn (이전 턴 요약 반영) | Holistic Flow |
|------|-------------------------------|----------------|
| **평가 단위** | 턴별 (Turn 1, 2, 3 각각 한 점수) | 세션 전체 (대화 하나에 한 점수) |
| **질문** | "이전 맥락을 감안했을 때 **이 턴**의 품질은?" | "**전체 대화**의 체이닝·전략은 얼마나 좋은가?" |
| **출력** | turn_1_score, turn_2_score, … → **aggregate_turn_score** | **holistic_flow_score** 하나 |

- **Eval Turn**: 맥락을 아는 **턴별** 점수 → "진행해줘" 같은 턴이 단독이 아닌 연속으로 보일 때 공정하게 높은 점수.
- **Holistic**: 턴별 결과·요약을 모아 **세션 전체** 관점에서 체이닝 품질 한 번 더 평가.
- 최종 `prompt_score = 0.6 * holistic_flow_score + 0.4 * aggregate_turn_score` 는 그대로: 세션 수준(체이닝) 60% + 턴 수준(품질) 40%.

### 구현 시 변경 요약
| 위치 | 변경 |

## 의도 분류 5-way 리팩토링 (V2.2)

### 목표
8가지 세부 의도 → 5대 그룹 매핑 레이어를 제거하고, **의도 분류를 처음부터 5대 통합 의도(SETTING, CREATION, REFINEMENT, VALIDATION, FOLLOW_UP)로만** 수행. 평가와 동일한 언어로 통일하여 FOLLOW_UP 쏠림 완화 및 유지보수 단순화.

### 변경 파일 요약
| 파일 | 변경 내용 |
|------|-----------|
| **eval_intent_analysis.yaml** | 8가지 → 5대 의도만 선택하도록 전면 수정. REFINEMENT(기존 코드 수정·보완·변형), FOLLOW_UP(코드 변경 없을 때만) 구분 명시. 출력 형식 JSON 예시 추가. |
| **states.py** | `IntentClassification.intent_types`: `list[CodeIntentType]` → `list[UnifiedIntentType]`. `reasoning` → `Optional[str]`. `UnifiedIntentType` import 추가. |
| **analysis.py** | 8→5 매핑(`_CODE_TO_UNIFIED_INTENT`, `map_to_unified_intent`) 제거. 5-way 파싱만 수행. 첫 턴 FOLLOW_UP 시 SETTING/CREATION 재분류. `CodeIntentType` 의존 제거. |
| **routers.py** | 8-way 라우팅 맵 제거. `UNIFIED_TO_NODE`(5→단일 노드) 추가. `unified_intent` 기준으로 단일 평가 노드 반환 (SETTING→eval_rule_setting, CREATION→eval_generation, REFINEMENT→eval_optimization, VALIDATION→eval_debugging, FOLLOW_UP→eval_follow_up). |
| **weights.py** | `LEGACY_INTENT_WEIGHTS`에 5대 키(SETTING, CREATION, REFINEMENT, VALIDATION, FOLLOW_UP) 추가. 기존 8-way 키는 레거시 호환용 유지. |
| **eval_turn_guard.py** | `intent_to_eval_key`에 5대 의도 추가. detailed_feedback 매칭 시 5-way→eval_key로 해당 피드백 찾도록 수정. |
| **aggregation.py** | 기본 의도 fallback `HINT_OR_QUERY` → `VALIDATION`. |

### DB/저장
- **스키마 변경 없음.** `prompt_evaluations.details`·`prompt_messages.meta`는 JSONB로, `intent`/`intent_types`/`unified_intent`에 5개 값만 넣어도 그대로 저장됨.
